---
title: Releasing
description: Maintainer commands that publish a package or tag the server image.
---

Publish from a clean `main` that matches GitHub. `npm login` stores the npm token in `~/.npmrc`. Store `PYPI_TOKEN` in the environment. Keep both tokens out of the repo and out of `.env`.

Bump `@anumat/js` or `@anumat/engine` with `pnpm changeset` and then `pnpm changeset version`. Bump `anumat-py` with `pnpm bump:anumat:version`. Bump `anumat-engine` with `pnpm bump:engine:version` when you want a patch on that package. Python versions are independent. `pnpm release:engine-py` publishes the version in `packages/engine-py`. It does not copy `@anumat/engine`.

Wait for CI on that commit before `pnpm release:engine-py`. That command downloads the `anumat-engine-release` artifact from the Engine wheels run for `HEAD`. It does not compile wheels on the laptop. Engine wheels cross-compiles the macOS arm64 sidecar on `macos-15-intel` so the job does not wait on GitHub's macOS arm64 hosted pool. The Windows wheel is built and uploaded without the Postgres smoke; Linux and macOS x64 still smoke against Postgres.

Every package release command requires the disposable Postgres from the repository README (`127.0.0.1:5432`, role `anumat` / `anumat`). The scripts check that port. They do not start Docker. They do not drop `anumat` or `anumat_test`. Type the version to confirm before any publish or local tag. None of the four package commands push tags. Scripts under `scripts/` run on bash 3.2 (macOS `/bin/bash`).

| Command | Publishes | Tag |
| --- | --- | --- |
| `pnpm release:engine` | `@anumat/engine` on npm | `@anumat/engine@<version>` |
| `pnpm release:engine-py` | `anumat-engine` on PyPI | `anumat-engine@<version>` |
| `pnpm release:anumat` | `@anumat/js` on npm | `@anumat/js@<version>` |
| `pnpm release:anumat-py` | `anumat-py` on PyPI | `anumat-py@<version>` |
| `pnpm release:server` | nothing to a package registry | `server@<version>` |

`pnpm release:engine` builds and tests `@anumat/engine`, packs the tarball with `check-pack.mjs` (`npm pack` plus attw, not a dry-run), then publishes if that version is absent. If npm already has the version and the local pack integrity matches, it only creates the local tag. A mismatch is fatal.

`pnpm release:anumat` builds `@anumat/js`, runs that package's tests, packs the same way, then publishes or does tag-only recovery.

`pnpm release:anumat-py` generates the client, runs `anumat-py` tests, builds wheel and sdist, smokes an import in an owned temp venv, then uploads only files that are not already on PyPI with the same sha256. Matching files are skipped. A different sha256 is fatal. Retry a partial upload without bumping the version.

`pnpm release:engine-py` runs `anumat-engine` tests, downloads the CI bundle, verifies commit, version, platforms, sdist, migration checksum, and SHA256SUMS, smokes the host wheel from that bundle, then publishes those files with the same hash-resume rules. Catalog tests recreate only `anumat_engine_parity`. If `gh` is missing, artifacts expired, or CI is not a success for this commit, the script stops. It will not compile wheels locally. Re-run Engine wheels with `gh workflow run 'Engine wheels' --ref main`.

`pnpm release:server` reads the version in `apps/api/package.json`, asks you to type that version, and pushes `server@` plus that version. The tag push publishes `ghcr.io/amitmirgal/anumat`.

After a package command succeeds, push the local tag yourself:

```bash
git push origin tag <tag>
```

If the registry already has the exact files, run the same `pnpm release:…` command again and type the version to create the local tag only. Do not bump the version to recover a missing tag.

`release:engine-py` tags `anumat-engine@<version>`. `release:anumat-py` tags `anumat-py@<version>`. They publish different packages.

There is no `release:js` command and no `release:py` command.
